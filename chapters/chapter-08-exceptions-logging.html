Xử Lý Ngoại Lệ (Exceptions) & Ghi Log Chuẩn Sản Phẩm

Trong môi trường Web production, một ngoại lệ không được bắt sẽ lập tức biến thành lỗi "Server Error 500" làm gián đoạn trải nghiệm người dùng. Học cách kiểm soát toàn bộ luồng lỗi và thiết lập logging để dễ dàng truy vết sự cố.

Mức độ: Quan trọng (Critical) Ứng dụng: Views, Forms & Middleware Thời gian đọc: 15 phút
#

1. Khối Lệnh Đầy Đủ: try / except / else / finally

Rất nhiều lập trình viên chỉ biết try/except mà không biết đến sức mạnh của else và finally.

try - except - else - finally Flow Control
💻 robust_exception_handling.py 
def process_user_order(cart_data):
    db_connection = "Open"
    try:
        print("1. [TRY] Đang trừ tiền và xuất kho...")
        quantity = int(cart_data.get("qty", 0))
        price = 100 / quantity  # Sẽ phát sinh ZeroDivisionError nếu qty=0
    except (ValueError, ZeroDivisionError) as err:
        print(f"2. [EXCEPT] Lỗi số lượng không hợp lệ: {err}")
        return "Giao dịch thất bại"
    else:
        # Chỉ chạy khi KHÔNG CÓ LỖI NÀO xảy ra trong try!
        print("3. [ELSE] Giao dịch thành công! Gửi email hóa đơn cho khách.")
        return "Giao dịch hoàn tất"
    finally:
        # LUÔN LUÔN CHẠY dù thành công hay có lỗi (dùng giải phóng tài nguyên)
        db_connection = "Closed"
        print(f"4. [FINALLY] Đóng kết nối Database ({db_connection}).")

print("--- Kịch bản 1: Có lỗi (qty=0) ---")
process_user_order({"qty": 0})

print("\n--- Kịch bản 2: Thành công (qty=2) ---")
process_user_order({"qty": 2})

Tại sao Django khuyên dùng khối else?

Khối try chỉ nên bọc dòng code dễ gây lỗi nhất (ví dụ câu truy vấn database). Toàn bộ logic gửi email hoặc render kết quả sau đó nên đưa vào khối else để tránh việc vô tình bắt nhầm (catch) những lỗi không mong muốn phát sinh từ các hàm phụ trợ.

2. Bộ 3 Ngoại Lệ Cốt Lõi Cần Nhớ Trong Django

Khi truy vấn dữ liệu từ Model bằng lệnh .get(), bạn sẽ luôn bắt cặp với 2 ngoại lệ sau:

ObjectDoesNotExist & Http404 ORM & Views
💻 django_orm_exceptions.py 
# Mô phỏng ngoại lệ của Django
class ObjectDoesNotExist(Exception): pass
class MultipleObjectsReturned(Exception): pass
class Http404(Exception): pass

def get_post_or_404(post_id, database_records):
    try:
        if post_id not in database_records:
            raise ObjectDoesNotExist(f"Không tìm thấy bài viết ID {post_id}")
        return database_records[post_id]
    except ObjectDoesNotExist:
        # Bắt lỗi không tìm thấy bản ghi và bắn lỗi 404 cho Django
        raise Http404("Trang bạn tìm kiếm không tồn tại!")

# Thử nghiệm hàm:
db = {1: "Giới thiệu Django", 2: "Lập trình Python"}

try:
    print("Lấy bài ID=1:", get_post_or_404(1, db))
    print("Lấy bài ID=99:", get_post_or_404(99, db))
except Http404 as e:
    print(f"🚨 Đã bắt được Http404 -> Hiển thị trang 404.html: {e}")

Phím tắt thần thánh trong Django:

Để không phải viết 5 dòng try/except Post.DoesNotExist: raise Http404 mỗi lần truy vấn, Django cung cấp sẵn hàm tiện ích cực ngắn: from django.shortcuts import get_object_or_404 → post = get_object_or_404(Post, pk=post_id).

3. Tự Tạo Ngoại Lệ Riêng (Custom Exceptions) & Form Validation

Tạo các lớp lỗi mang ngữ cảnh nghiệp vụ cụ thể giúp phân biệt rõ lỗi hệ thống kỹ thuật với lỗi do người dùng nhập sai quy định.

class ValidationError(Exception) Business Rules
💻 form_validation_pattern.py 
# Tự định nghĩa Exception kế thừa từ Exception gốc
class ValidationError(Exception):
    def __init__(self, message, code="invalid"):
        super().__init__(message)
        self.code = code

# Mô phỏng hàm clean_email() trong Django forms.py
def validate_company_email(email):
    if not email.endswith("@company.com"):
        raise ValidationError(
            "Chỉ chấp nhận email thuộc tên miền @company.com!",
            code="invalid_domain"
        )
    return email.lower()

# Kiểm tra:
try:
    valid_email = validate_company_email("hacker@gmail.com")
except ValidationError as err:
    print(f"Thông báo lỗi form: {err} (Mã lỗi: {err.code})")

4. Logging: Tại Sao Tuyệt Đối Không Dùng print() Trên Production?

Lệnh print() không lưu lại thời gian, không có cấp độ nghiêm trọng, và sẽ làm tắc nghẽn tiến trình WSGI của server khi có hàng ngàn request đồng thời. Dưới đây là chuẩn logging của Python và Django.

import logging; logger = logging.getLogger(__name__) Production Standard
💻 logging_standard.py 
import logging

# Cấu hình định dạng log chuẩn có thời gian và cấp độ
logging.basicConfig(
    format="[%(asctime)s] [%(levelname)s] [%(name)s]: %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",
    level=logging.INFO
)

logger = logging.getLogger("payment_gateway")

# 5 cấp độ log từ thấp đến cao:
logger.debug("Dữ liệu thô gửi đi qua socket") # Bị bỏ qua vì level là INFO
logger.info("Khách hàng bắt đầu thanh toán đơn hàng #12345")
logger.warning("Cổng thanh toán phản hồi chậm hơn 3 giây!")
logger.error("Giao dịch thất bại: Thẻ hết số dư!")
logger.critical("Mất kết nối hoàn toàn với Database ngân hàng!")

Cấu hình trong settings.py:

Trong settings.py, biến từ điển LOGGING = {...} cho phép Django tự động ghi các bản ghi logger.error vào file xoay vòng (rotating log files) trên ổ cứng hoặc tự động gửi email cảnh báo ngay lập tức cho các lập trình viên quản trị (ADMINS) khi có lỗi 500 xảy ra!
