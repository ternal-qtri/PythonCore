Hàm Nâng Cao & Nguyên Lý *args, **kwargs

Không có kỹ thuật nào xuất hiện nhiều trong tài liệu Django bằng *args và **kwargs. Từ các hàm xử lý View, Middleware, Model methods đến Decorator, nếu không hiểu bản chất packing/unpacking, bạn sẽ liên tục gặp lỗi TypeError: got unexpected keyword argument.

Mức độ: Tối quan trọng (Vital) Kỹ thuật: Packing & Unpacking Thời gian đọc: 14 phút
#

1. Cơ Chế Thu Thập Tham Số: *args & **kwargs

Dấu sao * thu thập các đối số vị trí (positional arguments) thành một tuple. Dấu hai sao ** thu thập các đối số có đặt tên (keyword arguments) thành một dictionary.

def func(*args, **kwargs) Core Syntax
Hàm có thể nhận bất kỳ số lượng tham số nào mà người gọi truyền vào mà không bị giới hạn số lượng.
💻 args_kwargs_demo.py 
def inspect_arguments(*args, **kwargs):
    print("Kiểu của args:", type(args), "| Giá trị:", args)
    print("Kiểu của kwargs:", type(kwargs), "| Giá trị:", kwargs)
    print("-" * 40)

# Gọi hàm với các kiểu dữ liệu khác nhau:
inspect_arguments(1, "django", True)
inspect_arguments(status="active", max_items=50)
inspect_arguments(99, user="admin", role="superuser")

Ứng dụng trực tiếp trong Django:

Trong urls.py, bạn định nghĩa các tham số URL linh hoạt: path('post/<int:post_id>/edit/', views.edit_post). Khi Django gọi view của bạn, nó sẽ truyền tham số đó vào thông qua **kwargs: kwargs={'post_id': 15}.

#

2. Chuyển Tiếp Tham Số Khi Ghi Đè (Forwarding Pattern)

Đây là lý do sống còn mà khi bạn ghi đè hàm save() của Model hay hàm get_context_data() của View, bạn luôn bắt buộc phải viết *args, **kwargs.

super().method(*args, **kwargs) Django Core Pattern
Bắt giữ toàn bộ tham số người dùng truyền tới, can thiệp xử lý logic của mình, rồi "chuyển tiếp nguyên vẹn" sang cho hàm lớp cha xử lý tiếp.
💻 forwarding_pattern.py 
# Giả lập lớp cha Django BaseModel
class DjangoModel:
    def save(self, force_insert=False, using=None):
        print(f"-> [LỚP CHA] Lưu CSDL: force_insert={force_insert}, db={using}")

# Lớp con ghi đè của lập trình viên
class BlogPost(DjangoModel):
    def __init__(self, title):
        self.title = title
        self.slug = ""

    def save(self, *args, **kwargs):
        # 1. Tự động sinh slug trước khi lưu
        self.slug = self.title.lower().replace(" ", "-")
        print(f"-> [LỚP CON] Đã tự tạo slug: '{self.slug}'")

        # 2. Chuyển tiếp nguyên vẹn *args, **kwargs cho lớp cha!
        super().save(*args, **kwargs)

post = BlogPost("Hoc Django Khong Kho")
post.save(force_insert=True, using="read_replica")
Terminal Output Đối Chiếu stdout 
$ python forwarding_pattern.py
-> [LỚP CON] Đã tự tạo slug: 'hoc-django-khong-kho'
-> [LỚP CHA] Lưu CSDL: force_insert=True, db=read_replica
⚠️

Cạm bẫy tai hại:

Nếu bạn định nghĩa def save(self): super().save() mà không có *args, **kwargs, khi Django gọi post.save(update_fields=['slug']) nội bộ, code của bạn sẽ lập tức quăng lỗi TypeError: save() got an unexpected keyword argument 'update_fields'.

3. First-Class Functions & Closures (Hàm Làm Tham Số)

Trong Python, hàm được đối xử như một giá trị bình thường: có thể gán cho biến, truyền vào làm tham số, hoặc một hàm có thể trả về một hàm khác.

Closures & Higher-Order Functions Foundational Concept
💻 closure_demo.py 
def permission_checker(allowed_role):
    # Hàm bên ngoài trả về hàm bên trong (Closure ghi nhớ allowed_role)
    def check_user(user_dict):
        return user_dict.get("role") == allowed_role
    return check_user

# Tạo ra các hàm kiểm tra chuyên biệt:
is_admin = permission_checker("admin")
is_editor = permission_checker("editor")

user_a = {"name": "Alice", "role": "editor"}
user_b = {"name": "Bob", "role": "admin"}

print("Alice có phải admin?", is_admin(user_a))
print("Bob có phải admin?", is_admin(user_b))
print("Alice có phải editor?", is_editor(user_a))
Terminal Output Đối Chiếu stdout 
$ python closure_demo.py
Alice có phải admin? False
Bob có phải admin? True
Alice có phải editor? True
🎯

Ứng dụng trực tiếp trong Django:

Khái niệm Closure này chính là bản chất 100% của Decorators (sẽ học chi tiết ở Chương 4) và các hàm lắng nghe sự kiện Django Signals như post_save.connect(my_receiver_function).

4. Triết Lý Function-Based Views (FBV) Trong Django

Bản chất của một website là chu trình Request → Response. Trong Django, một View cơ bản nhất là một hàm Python thỏa mãn 2 quy tắc vàng.

def my_view(request, *args, **kwargs) -> HttpResponse Django View Pattern
💻 fbv_anatomy.py 
# Giả lập đối tượng HttpRequest và HttpResponse trong Django
class HttpRequest:
    def __init__(self, method="GET", user="Guest"):
        self.method = method
        self.user = user

class HttpResponse:
    def __init__(self, content, status_code=200):
        self.content = content
        self.status_code = status_code

# Cấu trúc 1 Function-Based View thực thụ trong Django views.py
def article_detail_view(request, article_id):
    if request.method != "GET":
        return HttpResponse("Chỉ chấp nhận phương thức GET", status_code=405)
    
    # Xử lý logic và trả về response
    data = f"Bài viết #{article_id} - Người xem: {request.user}"
    return HttpResponse(data, status_code=200)

# Mô phỏng Django Router gọi View:
req = HttpRequest(method="GET", user="qtri")
res = article_detail_view(req, article_id=88)
print(f"Status: {res.status_code} | Nội dung: {res.content}")
Terminal Output Đối Chiếu stdout 
$ python fbv_anatomy.py
Status: 200 | Nội dung: Bài viết #88 - Người xem: qtri
🎯

Quy tắc vàng của Django View:

1. Tham số đầu tiên luôn luôn là request (thể hiện đối tượng HttpRequest mang theo thông tin header, session, cookies, user).
2. Giá trị trả về ở lệnh return bắt buộc phải là một instance của HttpResponse (hoặc các hàm render, redirect, JsonResponse kế thừa từ nó).
